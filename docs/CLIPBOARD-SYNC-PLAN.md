# 跨端剪贴板/文件同步 · 方案与工作量评估

> 调研日期：2026-10-18 · 目标：Windows ↔ Mac 复制文字/图片/文件，切换后直接粘贴
> 结论先行：**文字和图片是"一周内能跑通"的量级，文件是唯一的硬活，"无缝"的难点不在代码而在联调。**

## 1. 先重新定义需求：这个项目其实有天然优势

普通跨设备剪贴板工具必须做**持续同步**——因为两台设备可能同时在使用。

但你这套是「**双系统、单显示器**」：同一时刻只有一台机器在屏幕上、只有一只手在键盘上。
这意味着：

> **剪贴板只需要在"切换的那一刻"传递，不需要一直同步。**

这个约束带来三个好处，也正是自研相对 CrossPaste 的唯一价值点：

1. **隐私**：密码管理器复制的东西不会常驻在对端机器上，只有你主动切屏才过去
2. **带宽/功耗**：不常驻长连接传数据，平时零流量
3. **时机确定**：`dualswitch` 已经知道"什么时候要切"，可以在 DDC 命令之前抢先把剪贴板推过去

代价：切过去之后**只能拿到切换前的剪贴板**。如果切到 B 之后又在 B 上复制了新内容，得等切回 A 时才同步——而这恰好符合"单显示器"的使用模型。

**推荐架构：切屏触发式同步 + 可选常驻模式（配置项，默认关）。**

## 2. 现成方案盘点（如果你只想"能用"）

| 方案 | 覆盖 | 文本 | 图片 | 文件 | 局域网加密 | 代码/协议 | 评价 |
|---|---|---|---|---|---|---|---|
| **CrossPaste** | Win/Mac/Linux | ✅ | ✅ | ✅ | ✅ 端到端 | Kotlin Multiplatform，AGPL-3.0 | **首选**。LAN-only 无服务器、六种剪贴板类型、内置历史。你 README 里已经选了它 |
| **SyncClipboard** | Win/Mac/Linux/iOS | ✅ | ✅ | ✅ | TLS + AES256 | C#，MIT | 需要服务器（可用内置 / WebDAV / S3）。跨公网可用，但要维护一个服务 |
| **KDE Connect** | Win/Mac/Linux | ✅ | 弱 | 走文件发送 | ✅ | C++/Qt | 功能杂、Mac 端体验一般、剪贴板只有文本 |
| **Deskflow / Barrier** | Win/Mac/Linux | ✅ | 部分 | ❌ | 明文 | C++ | 它做的是键鼠共享，剪贴板只是附带；不会传文件本体 |
| **Apple 通用剪贴板** | Mac↔Mac/iOS | ✅ | ✅ | ✅ | — | 闭源 | 不支持 Windows，直接排除 |

**判断**：如果你能接受"两个后台进程、两套设置界面、切屏时偶尔没同步"，装 CrossPaste 是最省事的，成本 ≈ 20 分钟。
自研的价值只在「和切屏绑成一个动作、一个托盘图标、一个设置页」。

## 3. 自研方案设计

### 3.1 架构

```
┌──────────────── Windows ────────────────┐        ┌──────────────── macOS ─────────────────┐
│                                         │        │                                        │
│  热键 Alt+Space                          │        │  热键 ⌥ Space                          │
│      │                                  │        │      │                                 │
│      ▼                                  │        │      ▼                                 │
│  switch_controller ──DDC──► 显示器       │        │  switch_controller ──DDC──► 显示器      │
│      │                                  │        │      │                                 │
│      │ ① 先同步剪贴板（不阻塞切屏）        │        │      │                                 │
│      ▼                                  │        │      ▼                                 │
│  sync/engine  ──② 帧协议──►  TCP+TLS  ───┼────────┼──► sync/engine                          │
│      │                                  │  局域网 │      │                                 │
│      ▼                                  │        │      ▼                                 │
│  clipboard/win  ◄──③ 写回剪贴板          │        │  clipboard/mac  ◄──③ 写回剪贴板         │
│  (CF_HDROP / DIB)                       │        │  (file-url / PNG)                      │
└─────────────────────────────────────────┘        └────────────────────────────────────────┘
```

关键时序（**切屏不能等网络**）：

```
按下热键 → 立即发 DDC 切换（30ms，用户感知不到延迟）
         └→ 后台线程：读剪贴板 → 比对 hash → 推送 → 对端写回
            ├ 文本 <1KB   : ~40ms 到达
            ├ 图片 ~5MB   : ~150ms（千兆/WiFi6）
            └ 文件 ~500MB : 数秒，带进度提示
```

### 3.2 模块划分（与现有目录风格一致）

```
src/dualswitch/
├── clipboard/              # 新增：剪贴板抽象层
│   ├── base.py             # ClipItem 数据模型 + 后端接口 + 环抑制
│   ├── macos.py            # NSPasteboard：轮询 changeCount、类型映射、写回
│   ├── windows.py          # CF_HDROP / CF_DIB：格式枚举、路径列表、位图转 PNG
│   └── mock.py             # 测试用（项目已有 mock 传统）
├── sync/                   # 新增：同步层（平台无关，占 60% 代码）
│   ├── discovery.py        # UDP 广播发现 + 手动填 IP 兜底
│   ├── protocol.py         # 帧格式、消息类型、版本协商
│   ├── transport.py        # TLS 长连接、心跳、重连退避
│   ├── pairing.py          # 6 位 PIN + 证书指纹（TOFU）
│   ├── transfer.py         # 大文件分块、进度回调、SHA256 校验
│   └── engine.py           # 编排：何时推、推什么、冲突谁来赢
└── ui/                     # 扩展现有
    ├── settings.py         # 增加「剪贴板同步」页（开关/配对/设备列表/大小上限）
    └── pairing_dialog.py   # 新增：PIN 输入
```

### 3.3 传输格式（canonical clipboard）

内部只认 5 种规范形态，平台差异在 `clipboard/*` 里消化完：

```python
ClipItem = {
    "id": "sha256前16位",        # 内容指纹，用于环抑制和去重
    "ts": 1760000000.123,       # 源端修改时间（LWW 仲裁用）
    "kind": "text|html|image|files|mixed",
    "text": str | None,
    "html": str | None,
    "image": {"mime": "image/png", "w": 3840, "h": 2160, "size": 8_900_000},
    "files": [{"name": "报表.xlsx", "size": 2_100_000, "sha256": "..."}],
}
# 文本/HTML 内联在 JSON 头里；图片和文件走二进制分块（不 base64，省 33%）
```

**帧格式**（手写，约 80 行）：

```
[4B magic "DSYN"][1B ver][1B type][4B header_len][JSON header][binary payload...]
type: HELLO / OFFER(元数据) / PULL / DATA(分块) / END / ACK / ERROR
```

### 3.4 安全

| 层 | 做法 | 代码量 |
|---|---|---|
| 传输加密 | 标准库 `ssl` + 首次运行自签证书（TLS 1.3） | 30 行 |
| 身份确认 | TOFU：首次连接显示 6 位指纹，用户对一下 | 40 行 |
| 中间人防护 | 配对时 6 位 PIN，PBKDF2 派生确认码（防同网段抢连） | 50 行 |
| 敏感内容过滤 | 识别「不参与剪贴板历史」标记，直接跳过 | 20 行 |

敏感标记（实测有效，密码管理器都遵守）：

- macOS：`org.nspasteboard.ConcealedType` / `TransientType` / `AutoGeneratedType`
- Windows：`ExcludeClipboardContentFromMonitorProcessing`、`CanIncludeInClipboardHistory=0`

### 3.5 环抑制（防"你抄我我抄你"无限循环）

这是所有剪贴板同步工具的经典坑：A 写剪贴板 → 触发 B 的变更 → B 推回 A → A 又变……
三个兜底一起上：

1. 写回前记录 `expected_change_count`，下一个变更若等于预期则忽略
2. 内容 `sha256` 与 `last_applied_id` 相同则丢弃
3. `ts` 单调校验，旧内容永不覆盖新内容（LWW）

## 4. 五条实测结论（本机已验证，可直接当设计前提）

在 macOS + PySide6 6.12 + pyobjc 12.2 上实测：

| # | 结论 | 影响 |
|---|---|---|
| 1 | **Qt 的 `QClipboard.dataChanged` 在 macOS 上完全不触发**（事件循环内 poke 5 次，0 次回调） | **必须自己轮询 `NSPasteboard.changeCount`**。100ms 一次，单次读取 ~3μs，CPU 可忽略。这是本方案最大的"反常识"点 |
| 2 | Qt 写图片到剪贴板，系统侧只有 `public.tiff`，**没有 `public.png`** | 部分应用（尤其 Electron/浏览器）粘贴会失败。图片写入必须用 pyobjc 直接写 `public.png` + `public.tiff` 双格式 |
| 3 | Qt 读图片只给 `application/x-qt-image`（非标准 MIME） | 不能原样跨端传，必须 `QImage.save()` 转 PNG 再序列化 |
| 4 | Qt 写 `QUrl` 列表 → 系统侧正确生成 `public.file-url` + `NSFilenamesPboardType`（读也正常） | 文件剪贴板这一层 Qt 够用，**不用碰 CF_HDROP 裸 API** |
| 5 | `org.nspasteboard.ConcealedType` 可写可读 | 敏感内容过滤低成本可实现 |

> Windows 侧对应三条**待验证**（需要在另一台机器上跑）：
> ① `Qt.dataChanged` 走 `AddClipboardFormatListener`，预期可靠；
> ② 从资源管理器复制文件时 Qt 是否稳定给出 `urls`；
> ③ 图片是否以 `CF_DIB` 而非 PNG 出现（决定要不要做 DIB→PNG 转换）。

### 5.3 两端工作量对比

| | 共用代码 | 平台专属 | 专属部分具体是 |
|---|---:|---:|---|
| **macOS** | 1100 行（网络/协议/引擎/UI） | **~260 行** | NSPasteboard 后端 180、changeCount 轮询、权限引导 30、LaunchAgent 自启 20、打包 30 |

## 6. 简不简单：三句话

1. **文字同步：简单。** 一个下午能看到两端互贴成功，代码量不到现有项目的 10%。
2. **图片：中等。** 代码只有 200 多行，但"复制截图 → 粘到微信/Word/浏览器/PS/Figma"是一个 5×8 的矩阵，一个个试过去。
3. **文件：不简单。** 跨机器粘贴文件 = 真的要把文件传过去并存到本地某个目录，还要处理目录递归、`.app` 包、中文名 NFC/NFD、同名冲突、GB 级断点。这是唯一会让你加班的模块。

## 7. 需要调试的东西多不多：多，但都可枚举

| 类别 | 验证点数 | 说明 |
|---|---:|---|
| 格式矩阵 | ~96 | 6 类内容（纯文本/富文本/截图/多文件/目录/大文件）× 8 个目标应用（浏览器、Word、Excel、VSCode、终端、Finder/资源管理器、微信、PS）× 2 平台 |
| 网络场景 | ~20 | 首次配对、IP 变化、DHCP 换网、Wi-Fi 断连、休眠唤醒、防火墙拦截、AP 隔离、双网卡选路 |
| 环抑制 | ~8 | 文本/图片/文件各自的双向回环、快速连按热键、对端主动复制 |
| 文件边界 | ~15 | GB 文件、1000 小文件、目录嵌套、`.app` bundle、符号链接、隐藏文件、同名、磁盘满、中途取消、断网续传 |
| 权限/打包 | ~10 | macOS 防火墙放行、Windows 入站规则、开机自启、双平台安装包 |
| **合计** | **~150** | 其中约 100 项**必须两台机器同时在手**才能验 |

**最大的隐性成本不是写代码，是"两台机器都得开着、来回切换、反复粘贴"的联调时间。**
建议一开始就写一个 `tools/clip_matrix.py`：自动把 6 类内容生成到剪贴板并逐项回读校验，把人工验证从 96 组压到 10 组。

## 8. 推荐路线

**先花 20 分钟验证需求真伪**：装 CrossPaste 试用一天。
如果"切屏后还要手动点一下 CrossPaste"或"两个托盘图标很烦"让你受不了，再自研。

**自研则按这个顺序，每阶段都能独立可用：**

```
P0（文字）──► 用一周，确认"切屏即带剪贴板"这个交互是对的
   │
   ├─ 对 ──► P1 图片 ──► P2 文件
   │
   └─ 不对 ──► 停在这里，成本已收回（700 行）
```

**不建议一开始就做文件。** 文件传输占总工作量 35%、占调试量 40%，但它是最少用的场景（日常 90% 是文字和截图）。

## 9. 风险清单

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 局域网被 AP 隔离，两台机器互相不可达 | 中 | 致命 | 启动时自检连通性，明确提示"请用同一路由器/关掉访客网络" |
| Windows 防火墙拦入站 | 高 | 高 | 首次运行引导加规则；提供"仅出站模式"（由 Mac 主动连 Windows） |
| 大图（Retina 4K 截图 15MB+）拖慢切换 | 中 | 中 | 超过阈值转为"后台传输 + 托盘进度"，不阻塞粘贴文本 |
| 环抑制失效导致无限循环 | 中 | 高 | 三重兜底 + 单测覆盖 + 运行时"1 秒内同 hash 丢弃" |
| 文件名 NFC/NFD 不一致 | 高 | 低 | 传输前统一 `unicodedata.normalize('NFC', name)` |
| 剪贴板含密码被同步 | 中 | 高 | 敏感标记过滤 + 默认"仅切屏时同步" |
| macOS 打包后 TLS 证书路径失效 | 中 | 中 | 证书放 `~/Library/Application Support/dualswitch/`，不放 app bundle 内 |

## 10. 一句话总结

**文字 = 简单（700 行，一天见效）；图片 = 中等（+280 行，验证啰嗦）；文件 = 真难（+520 行，值得单独排期）。**
整体约 1900 行、相当于现有项目 25% 的体量，两端工作量对半，**难的不是写，是两台机器来回联调的 150 个验证点**。
想省事就装 CrossPaste（已满足 90%）；想要"一个热键、一个托盘、切屏即到"，自研 P0 阶段就能验证这条路值不值。
