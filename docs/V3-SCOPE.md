## 4. 键盘多端互传：现状、可行性、设计

### 4.1 现状是单向的，而且是硬编码的

`keyboard/` 2,144 行里只有 **`inject_macos.py`（注入到 Mac）**，没有 Windows 注入。配置里写得很直白：

```python
# config.py
capture_host: str = "windows"   # 键盘挂在哪台机器上。目前只支持 windows（捕获端）；mac 那一半没实现。
```

所以现在是 **Windows 抓键 → Mac 注入**，一条路，而且是**用平台名表示角色**（和 `sources.windows/mac` 是同一个病根）。

### 4.2 双 Windows 能不能做？技术上可以，但缺两块

| 能力 | 现状 |
|---|---|
| Windows 抓键 | ✅ 有（`hook_windows.py` 268 行 + `capture_windows.py` 671 行） |
| Mac 注入 | ✅ 有（`inject_macos.py` 216 行） |
| **Windows 注入** | ❌ **没有**，要新写（SendInput / `keybd_event`，约 350–400 行） |
| **Mac 抓键** | ❌ 没有独立实现（只有热键用的 CGEventTap，抓全键要新写，约 300–360 行） |

**所以双 Windows 是"差一个注入模块"，不是"做不到"。** 真正的难点不是技术，是下面这个。

### 4.3 四种组合的能力矩阵

| 键盘插在 | 画面在 | 需要 | 现在 |
|---|---|---|---|
| Windows | Mac | Win 抓 + Mac 注 | ✅ **已实现** |
| Windows | Windows | Win 抓 + **Win 注** | ❌ 缺注入 |
| Mac | Windows | **Mac 抓** + Win 注 | ❌ 两个都缺 |
| Mac | Mac | **Mac 抓** + Mac 注 | ❌ 缺抓 |

### 4.4 必须先解决的两个模型问题

**问题一：谁抓键，不能按平台判断，要按「键盘物理插在哪台」。**

双 Windows 时两台都跑着同一套抓键代码，如果都抓就会**一个按键发两次**。必须约定"只有一台抓"。

现在配置是 `capture_host: "windows"`——用平台表示角色。改成：

```jsonc
"keyboard": {
  "enabled": true,
  "keyboard_on": "local",        // local | peer —— 键盘插在哪台
  "mod_map": "position",         // position | semantic
  "release_chord": "ctrl+alt+shift+k",
  "blocked_keys": ["ctrl+alt+del", "win+l"],   // 不转发的系统键
  "forward_media_keys": false,
  "blur_guard_ms": 0
}
```

**问题二：修饰键映射要变成矩阵，不是单张表。**

现阶段 `keymap.py`(472 行) 只有 Win→Mac 一套。四种组合需要四套语义：

| 方向 | 映射要点 |
|---|---|
| Win → Mac | Alt→⌘、Win→⌥（现有 `position` 模式，用户定的） |
| Mac → Win | ⌘→Ctrl 还是 ⌘→Win？**要用户定**，这是个产品决策 |
| Win → Win | 基本恒等，但要注意左右修饰键、Win 键是否透传 |
| Mac → Mac | 恒等 |

### 4.5 产品化必须补的设置项

现在设置页里**键盘跟随一项都没有**（只有 `config.json` 能改）。产品化至少要加：

| 设置项 | 为什么必须有 |
|---|---|
| 键盘跟随开关 | 默认关闭（现在就是），卡键风险高 |
| **键盘接在哪台**（这台 / 对方） | 双 Windows 的唯一区分方式 |
| 修饰键映射模式 | position / semantic，用户习惯不同 |
| **紧急解除组合键**（可改） | 注入端崩了要能一键把键盘抢回来 |
| 不转发的按键黑名单 | Ctrl+Alt+Del、Win+L 这类注入不了或不应转发 |
| 媒体键是否转发 | 音量键转发到对面会「看起来没反应」 |
| 当前状态指示 | 「正在转发 / 已暂停」，不然用户不知道键盘归谁 |

### 4.6 键盘这块的风险（比显示器高）

| 风险 | 后果 | 对策 |
|---|---|---|
| 注入端崩溃 → 按键卡在按下状态 | 键盘像坏了一样 | `release_chord` 兜底 + 心跳对账（已有 `T_KEYSTATE`） |
| 双端都抓键 | 一个键触发两次 | 单端抓取约定 + 启动互斥 |
| 系统键注入被拦 | Ctrl+Alt+Del、Win+L 无效 | 黑名单 + 界面说明 |
| IME / 输入法状态不同步 | 中文输入错乱 | 明确"注入的是按键，不是文字"，文档写清 |
| 键盘热插拔 | 拔了还以为是 capture 端 | 需要设备检测 |

## 5. V3 还差什么（产品化视角，按维度列全）

### A. 显示器 / 切屏
- **A1 两块外接屏时选哪块**（现在是 `auto` + 名字匹配，没有选择器）
- **A2 同型号两台屏** → 主键 `mfg:pid` 撞车，要靠序列号细分
- **A3 热插拔/换屏要重启才生效** → 需要"切到切换页时刷新识别"
- A4 标定失败时的手工填码（设计上有，实现要留入口）
- A5 profile 导出入（换电脑 / 备份）
- A6 内置 profile 库怎么升级（跟着版本走？还是在线？）

### B. 键盘（详见 §4）
- B1 四种组合的能力补齐（缺 Win 注入、Mac 抓键）
- B2 键盘归属（这道选项目前完全没有）
- B3 修饰键映射矩阵 + 设置项
- B4 紧急解除 + 黑名单
- B5 键盘热插拔检测

### C. 配对 / 多设备
- **C1 只能一对一**：三台机器（家里 + 办公室）现在没法共存
- C2 设备名是 `DESKTOP-V6DVLD8` 这种，**不允许起别名**，界面上不友好
- C3 重新配对 / 解绑后的残留状态

### D. 剪贴板
- D1 **文件不跨端**（现在只有文字和图片）
- D2 超大文件、批量复制的策略
- D3 隐私：密码管理器已跳过（`ConcealedType`），但**其它敏感应用没有规则**
- D4 历史保留策略（现在 30 天 / 200MB 是默认值，没有引导）

### E. 产品化基建
- **E1 首次启动向导**：配对 → 选屏 → 标定，现在只有标定这一步是新的
- **E2 诊断页**：DDC 不同、端口不通、权限没给，用户只能看日志
- E3 日志导出（给客服/反馈）
- E4 自动更新
- E5 多语言（现在只有 zh_CN）
- E6 权限引导（辅助功能 / 屏幕录制，mac 上必须手动授权）

### F. 版本与兼容
- **F1 两端版本不一致怎么办**：V3 改了 `T_SWITCH` 载荷，V2 的对方会解析失败
- F2 协议版本协商（现在 `DSYN` 帧头有 `ver` 字段，但没做降级）

## 6. 建议的优先级

**如果目标是"你自己用得爽 + 换屏不折腾"** → 只做 P1（3–4 天），profile 一上就解决 80% 问题。

**如果目标是"给别人用"** → P1 + P2（1–1.5 周），加 E1/E2（首次向导 + 诊断）才勉强能交付。

**如果要做"通用产品"** → P1–P4 全做 + §5 的 A1/A2/B2/B3/C1/E1/E2，**这是 3–4 周的量**，而且键盘那块风险最高，建议单独排期。

**不建议**一上来做键盘多端互传：它是独立能力，做完双 Windows 也只在"两台 Win + 一把键盘"这一种场景有价值，但风险和工期都超过显示器那块的总和。
